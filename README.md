# Мини-CRM «Объекты и задачи»

React-приложение для строительной компании: постановщики управляют объектами и задачами, а исполнители работают только со своими назначениями. Права и переходы статусов защищены на уровне PostgreSQL/Supabase, поэтому ограничения действуют и при прямом обращении к API.

## Возможности

- вход по email и паролю без открытой регистрации;
- роли «Постановщик» и «Исполнитель»;
- создание, редактирование и мягкое удаление объектов и задач;
- назначение исполнителя и строгий цикл статусов;
- «Мои задачи» и доступ только к связанным объектам для исполнителя;
- неизменяемая через API история создания и переходов задачи;
- адаптивный интерфейс на Material UI.

Стек: React 19, TypeScript, Vite, Material UI, TanStack Query, React Hook Form, Zod и Supabase.

## Быстрый запуск фронтенда

Понадобятся Node.js 24+ и npm 11+.

```bash
npm ci
cp .env.example .env
npm run dev
```

Заполните `.env` публичными данными проекта Supabase:

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-key
```

`service_role`, пароль базы и другие секреты фронтенду не нужны и не должны попадать в `.env`, Vercel или репозиторий.

## Полностью локальный запуск через Docker и Nginx

Для запуска нужны Docker Engine и Docker Compose v2:

```bash
docker compose up --build --wait
```

Compose поднимает PostgreSQL, Supabase Auth, PostgREST, Supabase Studio и собранный frontend за Nginx. Миграции применяются автоматически, а демо-пользователи и данные создаются только при их отсутствии.

- CRM: `http://localhost:8080`;
- Supabase Studio: `http://localhost:54323`;
- PostgreSQL: `localhost:54322`.

Локальные учётные записи:

- `manager@example.com` — постановщик;
- `worker1@example.com` — исполнитель;
- `worker2@example.com` — исполнитель;
- пароль для всех трёх по умолчанию: `LocalTest123!`.

Эти данные предназначены только для локальной среды и никогда не должны использоваться в облачном проекте.

Просмотр логов и остановка:

```bash
docker compose logs --follow
docker compose down
```

Чтобы полностью удалить только локальные данные и получить чистую демобазу:

```bash
docker compose down --volumes
docker compose up --build --wait
```

Удаление volume необратимо для локальной базы и никак не затрагивает облачный Supabase. Для другого порта задайте `CRM_WEB_PORT`, а локальный пароль демо-пользователей можно переопределить через `LOCAL_TEST_PASSWORD`.

В Compose зафиксированы версии только необходимых для CRM компонентов Supabase. Nginx отдаёт React и проксирует Auth/REST по тому же адресу. Встроенные JWT и пароли известны публично и предназначены исключительно для локальной разработки; при self-hosted production их обязательно заменяют.

## Подготовка Supabase

### Облачный проект

1. Создайте бесплатный проект Supabase.
2. В настройках Email Auth отключите возможность самостоятельной регистрации.
3. Установите Supabase CLI и примените миграции:

```bash
npx supabase@latest login
npx supabase@latest link --project-ref YOUR_PROJECT_REF
npx supabase@latest db push
```

4. Через Authentication → Users создайте пользователей:
   - `manager@example.com` — постановщик;
   - `worker1@example.com` — исполнитель;
   - `worker2@example.com` — исполнитель.
5. Откройте SQL Editor и выполните [supabase/seed.example.sql](supabase/seed.example.sql). Скрипт назначит роли, имена и добавит три объекта с задачами в разных статусах.
6. Скопируйте Project URL и публичный anon key в `.env`.

Пароли тестовых пользователей задаются в панели Supabase и передаются отдельно, но никогда не коммитятся.

### Локальный Supabase

Основной локальный запуск выполняется единым Compose-файлом, как описано выше. Supabase CLI остаётся отдельным инструментом только для SQL- и сквозных проверок:

```bash
npx supabase@latest start
npx supabase@latest db reset
```

Перед этим остановите Compose командой `docker compose down`, поскольку обе среды используют одинаковые локальные порты. Регистрация отключена и в Compose, и в `supabase/config.toml`.

## Проверки

```bash
npm run lint
npm test
npm run build
```

Unit-тесты проверяют подписи статусов, доступные действия обеих ролей и обязательный комментарий доработки.

После запуска локального Supabase выполните 28 pgTAP-проверок RLS и бизнес-логики:

```bash
npx supabase@latest test db
```

SQL-тесты находятся в `supabase/tests/database/rls_and_workflow.sql`, работают внутри транзакции и откатывают тестовые данные. Они проверяют изоляцию исполнителей, запрет прямой смены статуса, допустимые переходы, неизменяемость истории и мягкое удаление.

E2E-проверки выполняются Playwright против запущенного Compose-стека:

```bash
npx playwright install chromium
npm run test:e2e
```

UI-сценарии проверяют создание объекта постановщиком, список задач исполнителя, разрешённые переходы и отказ при прямом открытии чужой задачи. Для полностью чистого сценария предварительно выполните `docker compose down --volumes` и `docker compose up --build --wait`.

## Как устроена защита

- RLS фильтрует строки для каждого авторизованного пользователя.
- На клиент выданы только точечные права чтения и изменения разрешённых столбцов.
- Статус меняет только RPC `transition_task`, которая блокирует задачу и повторно проверяет роль, назначенного исполнителя, текущий статус и комментарий.
- Историю записывают триггер и доверенная функция; у API нет прав на её вставку, изменение или удаление.
- RPC мягкого удаления сохраняют задачи и аудит, но скрывают архивные данные обычными политиками.

Подробнее: [объяснение для руководителя](docs/manager-overview.md) и [решения и ограничения](docs/decisions.md).

## Структура

- `src/` — интерфейс, API-слой и правила отображения действий;
- `supabase/migrations/` — схема, функции, привилегии и RLS;
- `supabase/seed.example.sql` — демонстрационные данные;
- `supabase/tests/database/` — интеграционные тесты базы;
- `e2e/` — Chromium-сценарии пользовательского интерфейса;
- `docs/` — материалы для передачи и публикации.

## Публикация

Проект готов к импорту в Vercel: build-команда `npm run build`, каталог результата `dist`. Добавьте две переменные `VITE_SUPABASE_*` для Production и Preview. `vercel.json` уже настраивает маршрутизацию SPA.

Пошаговая инструкция: [деплой на Vercel](docs/vercel-deployment.md). Финальная приёмка: [чек-лист публикации](docs/deployment-checklist.md).
